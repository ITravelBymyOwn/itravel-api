======================================================================
1. PRINCIPIO DE PRODUCTO
======================================================================
ITBMO es una plataforma propia de planificación y acompañamiento de viaje, powered by AI.
No debe presentarse como una IA-personaje.

Macro journey:
Acquisition/Growth
  -> Planner / Planning Intelligence
  -> Identity + Trip
  -> Workspace
  -> Context / Needs Intelligence
  -> Partner / Offer Engine
  -> Commerce / Promotions
  -> viaje ejecutado
  -> Travel Companion / Mobility
  -> Lifecycle
  -> Sharing / Referral / Creator
  -> Growth Intelligence

======================================================================
2. CAPAS COMUNES · NO DUPLICAR
======================================================================
- Identity / Session
- Trip Context
- Canonical Travel Entities / Travel Graph
- Context Intelligence / Needs Engine
- Partner Registry / Capability Registry
- Offer Resolver / Ranking
- Event Gateway
- Attribution
- Consent & Privacy
- Feature Flags
- External Adapters
- Observability / QA

El Planner nunca debe conectarse directamente a cada proveedor/canal.
Las integraciones externas entran mediante adapters y resolvers.

======================================================================
3. IDENTITY + ATTRIBUTION
======================================================================
Cadena conceptual:
anonymous_id -> session_id -> attribution_id -> user_id(optional) -> trip_id

Preservar:
- first touch
- last meaningful touch
- campaign
- creator
- promo code
- tracking code/link
- snapshot por trip cuando sea necesario para impedir cambios retrospectivos.

Supabase es source of truth de adquisición/comercio.
GA4/Brevo/plataformas externas reciben eventos, no sustituyen la verdad del negocio.

Futuras canonical needs:

======================================================================
5. PARTNER / OFFER ENGINE
======================================================================
Cadena:
Traveler -> Trip -> Context -> Need -> Solution -> Offer -> Partner -> Action -> Conversion

Partner != Offer.
Partner Registry define estado/capabilities.
Offer Engine resuelve una solución opcional al need.

Capabilities posibles:
- destination_link
- attraction_link
- product_link
- regional_product
- date_prefill
- origin_destination
- discount
- api_search
- real_time_availability

Regla permanente de contextualidad:
- cualquier atracción/actividad elegible puede intentar resolverse dinámicamente;
- mappings no pueden convertirse en una whitelist cerrada;
- fallbacks progresivos entity/activity -> category/destination cuando sean seguros;
- nunca inventar disponibilidad/producto/precio/coverage.

Ranking futuro:
1) relevancia exacta
2) cobertura/disponibilidad conocida
3) beneficio al viajero
4) UX/deep-link quality
5) fiabilidad
6) performance observada
7) comisión/economics como criterio secundario.

======================================================================
6. TRANSPORT RESOLVER
======================================================================
Intercity commerce debe originarse en la secuencia real de destinos principales del trip.
Nunca convertir arbitrariamente source_route local en una ruta comercial intercity.

Ahora:
- Omio adapter/resolver.

Prioridad de expansión:
- Trainline
- FlixBus
- Busbud
- Rail Europe
- car-rental partner para contextos donde transporte público/intercity no es la solución.

Operadores B2B/directos (p.ej. Renfe/Trenitalia) se evalúan según escala/capacidad.

======================================================================
7. PROMOTIONS ENGINE
======================================================================
Configuración data-driven desde Supabase, no hardcoding.

promo_codes:
- code
- campaign_id
- creator_id
- promo_type: percentage | fixed | free_trip
- discount_value
- currency
- max_redemptions
- max_redemptions_per_profile
- reservation_minutes
- starts_at / expires_at
- registered_only / verified_only
- active
- metadata

promo_redemptions = ledger operacional/inmutable de uso:
- reserved
- consumed
- canceled
- reversed

Requisitos:
- atomic reservation
- concurrency-safe quota
- idempotencia
- un perfil no excede su límite
- browser nunca decide final_amount
- free_trip crea entitlement, nunca fake payment=0.

ITBMO100 es una instancia configurable del motor, no lógica especial hardcodeada.

======================================================================
9. PAYMENT / ENTITLEMENTS
======================================================================
Entitlement de generación puede originarse en:
- pago confirmado
- free_trip promo consumida
- admin/test bypass controlado.

Payment provider nunca confía en un monto enviado libremente por el browser.
Servidor resuelve pricing/promotion y crea la orden con amount autorizado.

11. DYNAMIC ITINERARY ENGINE · FUTURO
======================================================================
El itinerario generado evoluciona a objeto editable/reoptimizável.

Flow:
user change/live event
  -> constraint validation
  -> re-optimization
  -> proposed update
  -> user approval
  -> new version

Recalcular:
- traslados
- ventanas de apertura/reserva
- duración
- comidas/descansos
- restricciones
- eficiencia del resto del día/viaje.

Nunca sobrescribir silenciosamente. Mantener versionado/rollback.
