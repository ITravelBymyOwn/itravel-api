11. PASSWORD RECOVERY · QA FUNCIONAL PASS / IDIOMA PENDIENTE
======================================================================
Flujo existente y validado:
1. Usuario solicita “Olvidé mi contraseña”.
2. /api/user action=forgot_password.
3. Supabase /recover.
4. Brevo SMTP envía email de recuperación.
5. Link abre Planner.
6. type=recovery es detectado.
7. Se abre modal para nueva contraseña.
8. /api/user action=reset_password actualiza contraseña.
9. Usuario puede iniciar sesión con la nueva contraseña.

QA 2026-09-12:
- Primeros intentos recibieron 429 de Supabase por mínimo de reenvío; configuración actual 60 s.
- Supabase Auth confirmó /recover.
- Brevo confirmó “Enviado”; Gmail tuvo retraso, pero ambos mensajes finalmente llegaron.
- El botón de recovery contiene enlace funcional mediante tracking r.send.itravelbymyown.com.
- Usuario logró restablecer contraseña correctamente y volver al Planner.

Estado:
- PASSWORD RECOVERY END-TO-END = QA PASS FUNCIONAL.

Hallazgo pendiente:
- El retorno del recovery puede perder ?lang=es/?lang=en y abrir planner.html sin idioma explícito.
- planner.html tiene fallback EN, provocando mezcla ES/EN después del recovery aunque Home siga en español.

Corrección quirúrgica entregada:
- SOLO public/planner.js.
- sendForgotPassword debe enviar redirect/origin conservando idioma actual:
  planner.html?lang=es o planner.html?lang=en.
- No tocar api/user.js, Supabase ni backend auth para este ajuste.

Estado de este micro-fix:
- IMPLEMENTADO/ENTREGADO PARA DEPLOY.
- PENDIENTE VALIDAR EN PREVIEW ES y EN antes de main.

Requisito de UX recomendado:
- Recovery inválido/expirado debe mostrar mensaje claro y no caer silenciosamente al Planner.
- No es bloqueo funcional si el flujo nuevo y válido pasa QA.
