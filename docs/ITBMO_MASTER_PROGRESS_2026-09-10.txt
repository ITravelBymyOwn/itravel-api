- Una misma necesidad/entidad debe mostrarse una sola vez.
- Viator/GYG aparecen como opciones compactas dentro de esa necesidad, evitando tarjetas duplicadas.

- No repetir por ciudad.

I) Omio · CORRECCIÓN ESTRUCTURAL
- Omio SOLO puede derivarse de la secuencia de destinos principales guardados del trip:
  destino[n] -> destino[n+1].
- Un viaje de una sola ciudad = cero ofertas Omio.
- Prohibido derivar Omio desde source_route local, hotel, POI, barrio, museo,
  aeropuerto->hotel u otro transporte intra-ciudad.
- Day trips/local excursions no se fuerzan a Omio.
- La existencia de una ruta real en Omio debe validarse en QA; si un deeplink de ruta
  no es soportado, preferir fallback tracked seguro antes que enviar a una página inexistente.

J) Telemetría
- partner_clicks incluye contexto adicional como city, need_type, entity_name,
  resolution_type y travel_date.

6. PROMOTIONS ENGINE · MACROTANDA
======================================================================
IMPLEMENTADO EN CÓDIGO; PENDIENTE MIGRACIÓN + QA.

Objetivo permanente:
El usuario/administrador debe poder crear, activar, pausar o modificar campañas de descuento
DESDE SUPABASE, sin cambiar código y sin hacer un deploy.

Tipos configurables:
- percentage: cualquier porcentaje válido 0..100 decidido por ITBMO.
- fixed: monto fijo en la moneda configurada.
- free_trip: itinerario sin pago del Planner.

Controles configurables por promo:
- code
- name
- campaign_id opcional
- creator_id opcional
- promo_type
- discount_value
- currency
- max_redemptions (cupo global)
- max_redemptions_per_profile
- reservation_minutes
- starts_at / expires_at
- registered_only / verified_only
- active
- metadata

Tablas nuevas:
- creator_partners
- creator_tracking_links
- promo_codes
- promo_redemptions
- view promo_code_control

Seguridad:
- Las tablas nuevas quedan con RLS habilitado y sin acceso directo anon/authenticated.
- Las operaciones de redención se realizan server-side mediante Vercel/service role.
- RPC de reserva/consumo revocados para browser roles.

Flujo de promoción:
validate/reserve atomically -> attach to trip/checkout -> entitlement or payment -> consume.

Reglas críticas:
- Reserva atómica para evitar sobrepasar cupos bajo concurrencia.
- Retry/refresco no debe consumir dos cupos.
- Un solo código activo por usuario+trip durante checkout.
- free_trip NO crea payment.amount=0; crea un entitlement vía promo_redemptions.
- Un descuento parcial modifica únicamente el importe que el servidor envía a PayPal.
- El navegador nunca decide el monto final.
